The app in three pieces

The appweb/ — React + TypeScript. Home (mic, review), Memories, Ask Huf. Voice via Chrome’s Web Speech API.
The serverserver/ — Python + FastAPI. Holds the Claude key, asks Claude to sort and to answer, saves items.
The databaseserver/huf.db — SQLite, one items table. Survives refreshes and restarts.

Follow one action: asking about Sarah

You type or say “What did Sarah from work tell me, and do I owe her anything?” and see an answer with the cards it came from.

Reference route — three stops

Where the question starts

web/src/screens/AskHuf.tsx → search for async function send

send() adds your bubble, calls ask() from web/src/api.ts (which adds today’s date and timezone), then shows Huf’s answer and the cards under “Based on”.

Where Claude is asked

server/llm.py → ANSWER_SYSTEM and def answer_question

The rules Claude must follow live in ANSWER_SYSTEM: use only saved items, cite their IDs, describe completed reminders as done. answer_question() sends every saved item plus your question and gets back an Answer (found, answer, used_item_ids) in a fixed shape.

Where Huf refuses to make things up

server/main.py → def ask, the lines after known =

The server keeps only cited IDs that really exist, loads those cards from SQLite, and returns “I don’t have anything saved about that yet.” when nothing real was cited. Tested in server/tests/test_grounding.py.

A practice to reuse: protect the kernel, then build it first

What happened here. The original brief described a broad assistant. Scope narrowed it to one kernel — Huf remembers context, not just commands — and named what waited: discipline features, clarifying conversations, notifications, wake word, integrations (devpost/scope.md → The Unique Kernel, Later, Explicitly Cut). The build then put that kernel in slices 1–3, before voice or polish (devpost/checklist.md).

The evidence. The whole kernel worked by typing at the first checkpoint; server/scripts/demo_check.py passes all three demo cases (17/17 checks) against real Claude; nothing from Later was built. One later addition — a “Which Sarah?” chooser — was taken in as the smallest version (a picker on Review, no conversation).

Reuse it next time:

  1. Write the one sentence a judge or user should remember, and check every feature against it.
  2. Give every “not now” idea a named home (Later or Cut) so it stops competing for attention.
  3. Order the build so the kernel works end to end first — then add the interface around it.
  4. When something new appears mid-build, ask for its smallest version that still proves the point.

Run it again

Two terminals, one Chrome tab

cd web && npm run dev
